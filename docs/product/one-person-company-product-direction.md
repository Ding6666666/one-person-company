# DSH 一人公司多智能体系统：已确认产品方向

**状态：** 产品方向已确认，记录截至 2026-08-20 已经确认的决策。

本文用于锁定产品初衷、核心边界和第一阶段目标。尚未确认的具体交互与存储设计不在本文中固化。正式开发设计见[文档索引](../README.md)。

## 1. 产品愿景

本项目要建设一个围绕“一人公司”设计、以 DSH Agent 作为 AI 员工运行基础的多智能体系统。

它是拥有自己页面、UI、后端和产品体验的独立系统。系统可以考虑以插件形式接入 DSH，但这种插件形式只是产品的接入或部署方式，不代表产品只是 DSH 原生页面的包装。

本项目不是：

- 只面向软件开发的多 Agent 工具；
- 另一套 Agent Runtime；
- DSH 工具市场；
- 对 DSH 页面进行简单换皮的管理面板。

本项目的核心价值是把多个 DSH Agent 组织成一家公司，让用户像经营真实公司一样创建、配置、授权和管理 AI 员工。

## 2. Workspace 与公司边界

用户进入产品后创建或选择 Workspace。每个 Workspace 代表一个相互独立的一人公司组织单元。

用户也可以把一个 Workspace 当作某个部门使用，但系统不建立公司与部门之间的父子层级。多个 Workspace 之间保持平级和隔离：

- 不继承员工、权限或知识；
- 不共享工作、业务资源或运行状态；
- 不建立集团或上级 Workspace；
- 用户分别进入和管理每个 Workspace。

Workspace 不再等同于 Git 仓库。Git 仓库只是软件开发业务插件可以连接的一类资源。

## 3. Employee 与 DSH Agent

在产品语义中，每名 Employee 都代表一名长期存在、拥有连续记忆的 DSH Agent。Employee 是用户看到和管理的稳定员工身份，不等同于一次运行或单个 Session。DSH Runtime 中按需创建、恢复或卸载的 Agent 与 Session，是这名员工执行具体工作的运行载体，不改变其产品身份。

每名员工通常围绕一类持续工作进行配置，例如后端开发、新闻撰写或财务分析，并可以按具体目标加入多员工协作。工作类型来自用户配置或模板，Core 不建立固定职业枚举；员工连续性的关键是稳定身份、能力配置和可由 DSH 持续召回的当前记忆。

用户可以完全自由地创建员工，并结构化配置：

- 身份与名称；
- 职位和职责；
- 工作目标与行为说明；
- DSH Tool、Skill 和 Connector 能力；
- DSH Memory 配置与员工专属记忆范围；
- 能力权限和资源范围；
- 模型、Token、超时、并发和沙盒等 Runtime 配置；
- 委派权限和审批规则。

Core 不固定经理、执行者、审核者等员工类型。员工模板、行业岗位和快捷创建以后可以复用自由创建能力实现，但不能成为 Core 的硬编码限制。

Employee 是长期组织成员，具体工作的 Agent 与 Session 创建、恢复、隔离和上下文管理直接使用 DSH：

- 本项目长期保存员工身份、职责、配置、授权、DSH Memory 绑定和公司履历；
- 员工的连续性由稳定的 Employee 身份、DSH Agent 配置、当前 Session 上下文和所绑定的 DSH Memory 共同构成；
- DSH 可以为同一员工维护相互隔离的多个 Session，并负责各自的历史、压缩和恢复；
- 具体工作使用新 Session 还是恢复已有 Session，由 DSH 能力和协作策略决定，Core 不固定一种 Session 拓扑；
- 本项目记录 Employee 与其 DSH Agent 配置、Memory 绑定及相关 Session 的关联，但不把运行态 Agent ID 当作 Employee 的长期身份；
- 单次执行失败或上下文污染不会破坏员工本身。

第一阶段只支持 DSH Agent，不为其他 Agent Runtime 建立兼容层。

## 4. DSH 与本项目的职责边界

Agent 的运行模型、能力模型和工作基础直接复用 DSH。本项目不重复建设另一套 Agent Runtime。

DSH 负责：

- Agent Runtime；
- 员工与用户的单独对话；
- Session 的消息、Job、Event、持久化、恢复、上下文压缩和并发隔离；
- Tool、Skill 和 Connector；
- 模型、Token 和上下文；
- 员工当前 Session 上下文，以及通过 DSH 接入和调用的跨 Session Memory；
- 沙盒、工具执行与权限落地；
- Agent 运行日志、工具调用和执行结果。

本项目负责：

- Workspace 的公司化表达；
- Employee 与 DSH Agent 配置、Memory 绑定及运行态 Session 的组织关系；
- Employee、公司工作、会议与 DSH Session 的关联；
- 自由创建和管理员工的产品体验；
- 能力分配、工具等级、资源范围和审批策略；
- 公司内部的通信路由、员工委派和责任关系；
- 多员工会议的参与关系、公司级消息、交付物、决定、结论和 Battle 汇总结果；
- 公司视角的状态、共享历史、结果和待审批事项；
- 决定哪些会议结论或公司知识需要写入员工的 DSH Memory；
- 自己的完整页面和 UI。

DSH 是员工的大脑、当前上下文、个人记忆入口和运行环境；本项目是公司的组织、通信、责任、协作与决策系统。若 DSH 使用第三方 Memory Provider，DSH 负责接入和调用，Provider 负责实际的记忆存储、检索及其内部实现，本项目不重复建设记忆引擎。

项目应直接读取和使用 DSH 的事实，不为 Session、Runtime、Tool 或员工个人 Memory 再建立含义不同的第二套事实来源。本项目可以保存 DSH Session ID 及其公司业务关联，但不复制 Session 的原始对话、推理、工具调用或运行事件。员工个人 Memory 的权威来源始终是 DSH 及其配置的 Memory Provider；如未来确有展示需要，本项目可以保存非权威副本，但第一阶段不以此为必要能力。

公司级协作事实由本项目保存。员工之间的消息、会议内容、委派链路、交付物、决定和用户裁决天然涉及多个员工，不属于任何一名 DSH Agent 的个人 Session。需要沉淀为员工个人经验的内容，由本项目提出写入要求，最终通过 DSH Memory 能力保存和召回。

## 5. 工作交办与员工委派

Core 同时支持两种工作方式：

1. 用户直接指定某名员工执行；
2. 用户把目标交给获得授权的员工，由该员工委派其他员工协作。

委派不是固定“经理”角色，而是一项显式能力和权限。获得委派权限的员工：

- 只能调用当前 Workspace 内的员工；
- 只能调用用户明确授权的目标员工；
- 不能通过委派扩大自身或目标员工的能力权限；
- 委派行为和结果必须可查看、可追踪。

直接交办是基础能力；自动规划、复杂协作方式和行业流程可以由 DSH 能力或业务插件提供。

### Battle 轻量协作

Battle 是一种轻量的多员工处理与汇总方式，不是独立的复杂裁决系统。它可以把同一个目标交给多名获授权的员工分别处理，然后：

- 收集各员工的结果；
- 进行基础整理、去重和归纳；
- 标记明显分歧或未解决事项；
- 形成总结并向用户上报。

Battle 不替用户作最终业务决定，也不在第一阶段引入复杂的评分、投票或自动仲裁机制。需要决策或高等级动作时，仍由用户确认。

## 6. 工具来源与工具等级

项目不以自行开发大量通用工具为目标。工具来源顺序为：

1. 优先使用 DSH 已有能力；
2. 其次接入成熟的第三方 Tool、MCP 或 Connector；
3. 接口不一致时只开发必要的薄适配；
4. 只有公司、员工、同事和委派等项目独有语义没有现成能力时，才开发项目专属工具。

DSH 负责工具的安装和连接。本项目读取 DSH 的能力目录，并负责把能力分配给具体员工。第一阶段不建设自己的工具市场。

工具等级定义在工具动作上，而不是笼统定义在整个工具上。同一个工具的读取与外部写入动作可以属于不同等级。

### L0：基础能力

- 接收指令；
- 读取自身配置；
- 使用当前 Session 上下文；
- 汇报进度；
- 写入本次工作的临时记录。

### L1：只读能力

- 读取授权范围内的文件、知识和数据；
- 网页搜索和浏览；
- 查询邮件、日历或外部业务信息；
- 不产生外部修改。

### L2：内部写入能力

- 修改 Workspace 授权范围内的文件；
- 创建文档、草稿和数据；
- 运行受沙盒限制的代码；
- 更新内部工作状态；
- 不直接对外发布或交易。

### L3：外部及管理能力

- 发送邮件或消息；
- 发布内容或部署服务；
- 删除重要数据；
- 调用付费接口或执行交易；
- 管理其他员工、能力和权限；
- 使用高权限 Shell 或敏感凭据。

基础工具默认安装并可被分配。新员工默认拥有 L0 和 Workspace 授权范围内的 L1；L2 和 L3 必须由用户明确授予。每个动作还应配置资源范围、是否需要审批以及审计要求。

例如：

```text
email.search  → L1
email.draft   → L2
email.send    → L3
```

## 7. 业务插件

业务插件是一人公司的完整业务能力组合，不等同于单个 DSH Tool。

一个 Workspace 可以同时启用多个业务插件，例如软件开发、市场、内容和财务。业务插件可以：

- 注册自己的导航和页面；
- 定义业务资源类型与展示方式；
- 组合所需的 DSH Tool、Skill 和 Connector；
- 提供员工配置建议，但不能限制自由创建；
- 提供业务工作视图和 DSH 状态投影；
- 声明需要的能力及最低工具等级；
- 提供少量该业务独有的 DSH Tool。

业务插件不能：

- 重新定义 Workspace 和 Employee；
- 绕过能力授权、工具等级和审批；
- 自行启动不受 Core 管理的 DSH Agent；
- 将自己的业务对象提升为全局 Core 对象；
- 直接依赖其他业务插件的内部存储。

第一阶段不建设插件市场和动态安装系统，只保留清晰的业务模块边界，并由真实业务插件需求驱动后续扩展接口。

## 8. 软件开发能力的处理

现有软件开发代码不删除。它退出默认产品核心，后续作为“一人公司的软件开发业务插件”重新接入。

软件开发插件可以继续包含：

- Git 仓库资源；
- 软件项目和开发任务；
- Worktree、Branch 和 Commit；
- Delivery、Review 和 Integration；
- 软件员工配置建议；
- 软件开发专属页面；
- 对 DSH 文件、Shell 和 Git 能力的依赖声明。

新 Company Core 不依赖任何软件开发概念。软件开发插件可以依赖 Company Core 和 DSH，但 Company Core 不能反向依赖软件开发插件。

现有软件开发源代码和测试在重构期间继续保留、构建和验证，不通过删除旧能力来完成新产品转向。

## 9. 重构路线

项目采用“双仓演进”路线：在新的 `dsh-company` 仓库中建立通用 Company Core，同时保留原 `multi-agent` 仓库中已经验证的软件开发能力。

- `dsh-company` 负责一人公司的通用产品、Company Core、Employee、公司协作和业务插件边界；
- `multi-agent` 保持独立、可构建和可验证，继续保存现有软件开发源代码与测试；
- 软件开发能力后续以业务插件形式接入 `dsh-company`，而不是在新 Core 中继续扩展软件开发专属模型；
- 两个仓库可以复用已经验证的设计和通用工程资产，但不通过在原仓库中直接替换产品内核完成转向。

新项目可以有选择地复用：

- DSH 宿主接入与进程连接；
- 服务和 API 工程骨架；
- 双语 UI、通用组件和可访问性基础；
- 错误处理、测试和验证门禁；
- 可以服务新 Core 的通用权限与审计设施。

新 Core 不再继承：

- 将 Workspace 等同于 Git 仓库的假设；
- Manager、Executor、Reviewer、Integrator 等固定产品角色；
- 软件 Meeting、Task、Delivery、Integration 作为默认主流程的设计；
- 工程化主导航和只服务代码交付的页面。

新 Core 先建立独立边界和默认 UI；待业务插件接口成熟后，再把旧软件开发能力整理为软件开发插件。项目不沿着旧软件模型不断增加通用分支，也不删除或污染已经验证的软件开发实现。

## 10. 第一阶段成功标准

第一阶段必须跑通最小公司闭环：

1. 用户创建并进入一个 Workspace 公司；
2. 用户自由创建一名或多名 Employee；
3. 用户从 DSH 能力目录为员工配置工具、等级和权限；
4. 用户可以直接向员工交办工作；
5. 获得授权的员工可以委派其他员工；
6. DSH Session 实际执行工作；
7. 高等级动作按策略请求用户审批；
8. 用户可以查看执行状态、结果、历史和委派关系。

自动经营、定时任务、成本分析、绩效体系和完整经营驾驶舱不属于第一阶段的必要闭环。

## 11. 尚未固化到本草案的内容

以下内容仍需继续讨论，因此本文不把它们写成最终设计：

- 多员工会议的最小数据结构与交互方式；
- 哪些公司知识需要写入员工 DSH Memory，以及触发、审核和纠正的具体交互；
- 产品首页、老板工作台和员工工位的具体信息架构；
- 业务插件正式注册接口和启用流程。
